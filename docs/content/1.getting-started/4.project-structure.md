SkyPort keeps the repository split into a small number of clearly defined surfaces.

```
SkyPort/
├── backend/            # Go backend server and API modules
├── cli/                # Standalone Go CLI and TUI entrypoints
├── docs/               # Docus documentation site
├── frontend/           # Web dashboard source
├── installer/          # Shell installers
├── packaging/          # Desktop and platform packaging
└── scripts/            # Build and sync helpers
```

## Backend

The backend owns API routes, WebSocket streams, runtime collection, and host integration.

```
backend/
├── cmd/server
├── internal/
│   ├── api/
│   ├── docker/
│   ├── metrics/
│   ├── marketplace/
│   ├── pm2/
│   ├── proxy/
│   └── vps/
```

## CLI

The CLI provides the operator-facing command surface.

```
cli/
├── cmd/
├── internal/
│   ├── api/
│   ├── config/
│   ├── docker/
│   ├── pm2/
│   ├── ssh/
│   └── tui/
└── main.go
```

## Runtime Storage

The CLI stores its local state under `~/.skyport/`.

```
~/.skyport/
├── config.yaml
├── data/
├── workspace/
├── logs/
├── cache/
└── tmp/
```

## Build Targets

- `make backend-build` builds the backend server.
- `make cli-build` builds the CLI binary.
- `make build-all` builds the embedded UI plus release binaries.

## Why This Matters

This layout keeps docs accurate because each section maps to a real part of the codebase. If a feature is not wired into the relevant module, it should not be documented as production behavior.
