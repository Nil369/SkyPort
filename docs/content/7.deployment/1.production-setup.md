SkyPort production setup is about three things: a stable backend process, a reachable web UI, and a reverse proxy or TLS front door.

## Recommended Baseline

- run the backend as a system service on Linux
- keep the CLI installed on the operator machine
- expose the web UI through Caddy or another reverse proxy
- keep secrets in environment variables, not in docs or shell history

## Backend Service

```bash [terminal]
skyport service install
skyport service status
```

If you are not running as root, the command prints the unit file so you can install it manually.

## Web UI

```bash [terminal]
skyport start webui
```

You can override the backend binary when the launcher does not find it automatically.

## Reverse Proxy And HTTPS

The backend proxy module can generate Caddy or Nginx config and persist mappings. The docs should stay honest about that scope:

- Caddy is the preferred path for automatic TLS behavior.
- Nginx paths require certificates or certbot handling.
- Reverse proxy generation is not a full orchestration system.

## Environment Variables

```bash [terminal]
SKYPORT_HOST=0.0.0.0
SKYPORT_PORT=8080
SKYPORT_DB_PATH=./data/skyport.db
SKYPORT_WORKSPACE_ROOT=./workspace
SKYPORT_ENCRYPTION_KEY=<base64-key>
JWT_SECRET=<strong-secret>
```

## Operator Checklist

1. Confirm the backend listens on the correct host and port.
2. Protect the web UI with HTTPS.
3. Add a reverse proxy mapping if you expose apps on custom domains.
4. Verify Docker and PM2 access from the host.
